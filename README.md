# AMD RX 9070 16 GB 跑 Gemma4-26B-A4B：專家放 RAM 的實測研究

> 測試日期 2026-11-10。對象：在顯存不夠放下整個模型的機器上，用 llama.cpp 跑 Gemma4-26B-A4B（MoE），單路、長上下文（6～10 萬 token）時怎麼設定最快。
> 測速腳本：[`bench_gemma4_26b.py`](bench_gemma4_26b.py)（用法見文末）。GUI 啟動器與文中提到的欄位：[BBQ2077/GGUFRun](https://github.com/BBQ2077/GGUFRun)。

## 一、結論

| 項目 | 建議值 | GGUFRun 欄位 |
| --- | --- | --- |
| 上下文 | `-c 102400` | 上下文 |
| 專家放置 | `--cpu-moe`（全部專家放 RAM） | MoE 放 CPU 層數填 `all` |
| 專家顯卡快取 | `--moe-cache-mib 8500` | MoE 顯卡快取 |
| 預填批次 | `-ub 1024` | 預填批次 |
| 草稿 | `-md mtp-gemma-4-26B-A4B-it.gguf --spec-type draft-mtp,ngram-mod --spec-draft-n-max 2` | 投機模式＋草稿長度上限 2＋附加 n-gram 選 `ngram-mod` |
| KV | `-ctk q4_0 -ctv q4_0`，`-fa on` | KV 型別 |
| 視覺塔 | `--mmproj … --no-mmproj-offload`（放 RAM） | 視覺選 RAM |
| 採樣 | temp 0.6／top-p 0.9／top-k 64／min-p 0.05／repeat 1.1 | 基本（HauhauCS 模型卡建議值） |

這組的實際速度（RX 9070 16 GB、DDR4 2666、PCIe 3.0）：

| 情境 | 預填 | 生成 |
| --- | --- | --- |
| 短對話 | — | 約 48～57 tok/s |
| 一次丟 3 萬 token 長文 | 約 640 tok/s | 約 39 tok/s |
| 同一個對話累積到 6.8 萬／11 萬 token | 509／354 tok/s | 約 29.5 tok/s |
| 照抄前文的工作（改程式後完整輸出） | — | 約 85 tok/s（只開 MTP 是 61） |

顯存：專用 15077 MiB、共用 876 MiB（含桌面約 2 GB）。桌面吃到 2.5 GB 時還剩約 0.5 GB；不夠就把快取降 500。

舊模板（`--n-cpu-moe 12`、沒有快取、MTP 一次 3 個、runtime 路徑錯）短對話只有 32～33 tok/s；runtime 找不到 ROCm SDK 時直接掉成純 CPU，11.3 tok/s。

## 二、測試環境

| 項目 | 規格 |
| --- | --- |
| 顯卡 | AMD Radeon RX 9070（gfx1201）16 GB，桌面閒置佔約 2.0～2.1 GB |
| CPU／RAM | Ryzen 7 5700（PCIe 3.0 x16）／DDR4 2666 |
| 系統 | Windows 11 |
| runtime | llama.cpp `b12224` ROCm Windows 建置（`llama-b12224-bin-win-rocm-10.0-x64`），PATH 加 `RUNTIMES/rocm-sdk-10.1.0/bin` |
| 主模型 | `Gemma4-26B-A4B-QAT-Uncensored-HauhauCS-Balanced-Q4_K_M.gguf`（16.8 GB） |
| 草稿 | `mtp-gemma-4-26B-A4B-it.gguf`（BF16，252 MB，架構 `gemma4-assistant`，4 層） |

模型結構（讀 GGUF 張量統計）：

| 部分 | 大小 | 說明 |
| --- | --- | --- |
| 路由專家 | 14.09 GiB | 30 層，每層 128 個專家選 8 個，每層約 0.47 GB；`--cpu-moe`／`--n-cpu-moe` 只影響這部分 |
| 注意力 | 0.60 GiB | 一直在顯卡 |
| 共用（稠密）FFN | 0.37 GiB | 一直在顯卡 |
| 其他（嵌入等） | 0.57 GiB | |

KV：25 層滑動視窗（1024）＋5 層全域注意力（2 個 KV 頭），q4_0 每個 token 約 5.6 KB，10 萬上下文約 0.6 GB。上下文從 6.5 萬開到 10 萬只多約 640 MiB，到 128K 再多約 540 MiB，所以開大上下文很划算。對照 Qwen3.8 27B（48 層線性注意力＋16 層全注意力，4 KV 頭 × 256 維），每 token 約 16 KB，是 Gemma 的 3 倍。

## 三、有用的

### 1. ROCm SDK 一定要在 PATH 上
ROCm 建置的 `llama-server` 找不到 ROCm DLL 時**不會報錯，直接改用 CPU 跑**：同一個模型 11.3 tok/s（應有 33 以上）。舊模板指到一個已改名的 runtime 資料夾，UI 不認得、沒加 SDK 路徑，就是這樣。GGUFRun 現在會把 `RUNTIMES/rocm-sdk-*/bin` 自動加進 PATH。檢查方法：日誌要有 `ROCm0` 裝置與 `offloaded N/N layers to GPU`。

### 2. 全部專家放 RAM＋顯卡快取，比「固定放幾層」好
`--moe-cache-mib N` 在顯卡開一塊空間，放 RAM 裡專家的**副本**：常用的留著，沒命中才經 PCIe 搬上來，擠掉最久沒用的。RAM 那份正本不會少，必須搭配 `--cpu-moe` 或 `--n-cpu-moe` 才有作用。

短對話（6.5 萬上下文；有快取的組合都開 MTP 一次 2～3 個）：

| 放置方式 | 生成 tok/s | 備註 |
| --- | --- | --- |
| `--n-cpu-moe 12`，沒有快取（舊模板） | 33.1 | 開 MTP 一次 3 個反而 31.9 |
| `--n-cpu-moe 6`，沒有快取 | 39.3～42.5（不開草稿）／35.1（MTP 3） | 共用顯存 1.0～1.8 GB，已溢出 |
| `-fit` 自動放置＋MTP | 18.5 | 不開草稿 34.4 |
| `--cpu-moe` ＋快取 9000 | 52.7 | |
| `--n-cpu-moe 24`＋快取 6500 | 57.2 | 最後 6 層專家固定在顯卡 |
| `--n-cpu-moe 15`／`20`／`22`／`26`＋對應快取 | 38.2／52.7／54.3／52.7 | |

短對話時 `--n-cpu-moe 24` 比全部交給快取快 5～8%；但長文時兩者差不多（見第 6 點），而全部交給快取的設定實測過顯存，所以建議用 `all`。

快取大小：每多 500 MiB 約快 1～2 tok/s；超過顯卡容量（共用顯存衝破約 1 GB）會掉到 37～38。

### 3. 草稿用 MTP（BF16），一次 2 個
| 一次草稿 | 生成 tok/s | 接受率 |
| --- | --- | --- |
| 1 | 48.3 | 52% |
| **2** | **52.7** | 42% |
| 3 | 50.4～51.0 | 32% |
| 4 | 42.9 | 22% |

3 萬 token 長文下同樣是 2 最好：2／3／4 分別是 32.8／31.2／25.5 tok/s（`--n-cpu-moe 22`、快取 4000 的設定）。長文並不會讓長草稿變划算。

HauhauCS 模型卡說 MTP 約快 35%：實測 ncmoe+快取的設定下，不開草稿 38.8 → 開草稿 50～53，相符。

### 4. 預填批次 `-ub 1024`
專家放 RAM 時，每一批預填都要把整層專家經 PCIe 搬上顯卡一次，批次越大搬越少。1.5 萬 token 長文（128K、`--n-cpu-moe 24`）：

| `-ub` | 快取 | 預填 tok/s | 生成 tok/s | 共用顯存 |
| --- | --- | --- | --- | --- |
| 512（預設） | 5500 | 499 | 35.1 | 653 MiB |
| **1024** | 5500 | **847** | **45.5** | 942 MiB |
| 2048 | 5500 | 1266 | 27.1 | 2753 MiB |
| 2048 | 3500 | 1076 | 24.9 | 1555 MiB |
| 4096 | 4500 | 1613 | 22.0 | 4686 MiB |

- 預填和生成用的是同一組設定，不能「預填用大批次、生成換小批次」：運算暫存和專家快取都在啟動時固定分配。
- 批次 2048 以上，共用顯存大增、生成掉速；快取降到 3500 時專用顯存沒滿，生成照樣掉，所以不只是「搶了快取的空間」（推測是 ROCm 為搬運專家在系統記憶體開的暫存變大，日誌沒印，未證實）。
- `-ub 1536` 只在 3 萬 token 長文測過，而且同時把 ncmoe 改成 22、快取壓到 4000：預填 644、生成 32.8，比 1024＋快取 6000（679／38.7）兩頭都慢。單看批次大小，1024 到 2048 之間還沒找到更好的點。

### 5. 附加 n-gram 草稿（抄前文）
`--spec-type draft-mtp,ngram-mod`：輸出和前文重複時，直接把前文接下去的一段當草稿，可以和 MTP 一起用。改函式後完整輸出（同樣的 1678 個 token）：

| 草稿 | 生成 tok/s | 接受 |
| --- | --- | --- |
| 只開 MTP | 61.2 | 1102／1150 |
| MTP＋`ngram-mod` | **85.2** | 1550／1800 |

摘要、翻譯這類不照抄的工作幾乎沒幫助，但也不會變慢，可以一直開。對應 EXL3 的 `-hdt`／`-ngram`。

### 6. 長文的實際行為
同一個 server、提示快取開著，同一個對話繼續加內容（`--n-cpu-moe 24`、快取 5500、`-ub 1024`、128K）：

| 輪次 | 上下文總長 | 這次預填 | 預填 tok/s | 生成 tok/s | 草稿接受 | 總等待 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 68194 | 68193 | 509 | 29.6 | 198／400 | 148 s |
| 2 | 111615 | 43425 | 354 | 29.5 | 202／393 | 137 s |

- 等待時間九成在預填，所以長文要優先顧預填速度。
- 前面讀過的內容會沿用快取，只預填新增的部分；對同一份文章追問幾乎馬上開始回答。
- 上下文越長，預填越慢（每個新 token 都要看全部前文）。
- 長文後生成慢約 2 成，**不是專家快取被預填洗掉**：同一個 server 讀完 3 萬 token 後開新對話，生成馬上回到 48～50 tok/s。是長上下文注意力本身的代價。

10 萬上下文、3 萬 token 長文的對照：

| 設定 | 預填 | 長文生成 | 長文後新對話 | 專用／共用顯存 |
| --- | --- | --- | --- | --- |
| `--n-cpu-moe 22`＋快取 4000＋`-ub 1536` | 644～650 | 31.8～32.8 | — | 14717／1081 |
| `--n-cpu-moe 24`＋快取 6000＋`-ub 1024` | 679 | 38.7 | 49.5 | 未量到 |
| **`--cpu-moe`＋快取 8500＋`-ub 1024`** | 643 | **39.4** | 47.8 | **15077／876** |

### 7. 其他
- **KV q4_0**：顯存固定的前提下比 f16 好。f16 要把快取從 5500 降到 4000 才放得下，長文生成 30.7 對 35.2 tok/s。（兩組快取不同，比較的是「同顯存預算」而不是 KV 型別本身的速度。）
- **思考模式**：開思考時 MTP 接受率較高（一次 2 個：60%，關思考 42%），短對話 54.7～55.2 tok/s。開或關都可以，看用途。
- **視覺塔放 RAM**（`--no-mmproj-offload`）：不佔上面的顯存預算。

| KV q3／q2、DFlash2 | — | b12224 不支援；只有 EXL3 有 |

## 五、注意事項

1. **看共用顯存**：工作管理員的「共用 GPU 記憶體」超過約 1 GB，通常代表已溢出到 RAM，生成會掉。桌面、瀏覽器、其他程式佔的顯存都要算進去。
2. **快取大小要配合上下文**（`--n-cpu-moe 24` 時）：6.5 萬上下文 6500、10 萬 6000、128K 5500。全部專家放 RAM（`--cpu-moe`）時 10 萬上下文用 8500。
3. **測速時不要同時開別的模型**；測完確認 `llama-server.exe` 真的結束（`taskkill /T` 連子程序一起殺），否則下一組會搶顯存。
4. **短提示和長文的數字差很多**：短提示 50+ tok/s，長文 30～40。用途是長文就要用長文測。
5. **字元和 token**：所有速度、`-ub`、`-c` 都以 token 計算。程式碼約 3～4 字元／token；中文常用字常常 1 字 1 token；本次素材（程式碼＋中文註解）約 2.65 字元／token。
6. **生成 32 token 的長文測試不可靠**：預填批次表的生成速度是 32 token 的結果，接受數只有十幾個，僅供相對比較；第 6 點的 400 token 才是實際用途的數字。

## 六、和其他方案比較

- **EXL3**（ExLlamaV3，[BBQ2077/exl3-windows-gfx1201](https://github.com/BBQ2077/exl3-windows-gfx1201)）：LuniGemma 4.0bpw、`-mcl 8`，32K 上下文 38.8 tok/s。EXL3 的 `-mcl`／`-mcs` 是固定把某些專家交給 CPU 算，生成時不會上下換；`-mcpa` 只在預填時串流搬專家。GGUF 的顯卡快取在生成時也能換，所以這台機器 Gemma 用 GGUF 較快。EXL3 的 assistant 草稿（需要 exllamav3 ≥1.6.5）和 MTP 同架構，預期接受率也在 30% 左右，沒有移植。
- **Strata**（RX 9070 社群數據）跑 Qwen 系 MoE 約 58 tok/s：換算成每輪前向，兩邊都是每輪 25 次左右（這裡每輪接受約 2.0 個，Strata 約 2.5 個），差別在草稿接受率（Strata 62～75%，這裡 30～42%），不是引擎或 PCIe／DDR4 慢。
- Qwen3.8-27B（稠密）EXL3＋DFlash2 可到 100 tok/s 以上，但它整個放得進顯卡，條件不同。

## 七、還沒解的

- 長文生成約 30 tok/s 的瓶頸細節（注意力核心？KV 反量化？）還沒拆開測。
- `-ub` 在 1024～2048 之間、快取維持 5500 以上的組合還沒找到更好的點。
- 開思考時 MTP 接受率較高，長文＋思考的速度沒測。
- DFlash 在原版（非無審查）Gemma 上的接受率沒測。
- 每組多半只跑一次（短提示取暖機後第 2 次），1～2 tok/s 的差距可能在誤差內。

## 八、重現

只用 Python 標準庫。`--root` 指到放 `RUNTIMES/` 和 `LLM-MODELS/` 的資料夾（GGUFRun 的配置）；模型放 `LLM-MODELS/`，runtime 放 `RUNTIMES/llama-b12224-bin-win-rocm-10.0-x64/`，ROCm SDK 放 `RUNTIMES/rocm-sdk-*/bin` 會自動加進 PATH。`--runtime`、`--model`、`--mtp` 也可以直接給完整路徑。

```bat
:: 測速期間不要開其他模型（偵測到別的 llama-server 會拒絕執行，--force 可略過）
py -3 bench_gemma4_26b.py --list
py -3 bench_gemma4_26b.py --root D:\GGUFRun                                 :: best：短對話＋3 萬 token 長文＋照抄
py -3 bench_gemma4_26b.py --root D:\GGUFRun --preset best,ncmoe24,old
py -3 bench_gemma4_26b.py --root D:\GGUFRun --tests long --long-tokens 60000
py -3 bench_gemma4_26b.py --root D:\GGUFRun --extra "--moe-cache-mib 9000 -ub 2048"
py -3 bench_gemma4_26b.py --attach http://127.0.0.1:18435 --tests short    :: 測已經開著的 server
```

| 測試 | 內容 |
| --- | --- |
| `short` | 短提示生成 400 token，跑 2 次取第 2 次 |
| `long` | 一次預填約 `--long-tokens` 個 token（預設 30000）＋生成 400 token，接著開新對話跑短提示，並記錄顯存 |
| `copy` | 固定的合成程式碼（約 100 行），改一個變數名後完整輸出，看 n-gram 草稿效果 |

長文素材：`--corpus` 指定的檔案或資料夾；沒指定就用 `--root` 底下 GGUFRun 的程式碼與 README（本次研究用的就是這份）。結果寫入 `bench-results/gemma4-26b.jsonl`，server 日誌在 `bench-results/logs/`。`--extra` 的參數放在最後，同名參數會蓋掉前面的。

### 原始數據
[`data/gemma4-26b-rx9070-2026-11-10.jsonl`](data/gemma4-26b-rx9070-2026-11-10.jsonl)：本次研究用的舊版腳本輸出，一行一組。`name` 的格式是 `c<上下文>_n<--n-cpu-moe 層數｜cmoe＝--cpu-moe｜fit>_m<--moe-cache-mib>_s<草稿長度上限，0＝不開>`，後綴：`_q4` assistant Q4 草稿、`_df`／`_df8`／`_df16` DFlash Q4／Q8／BF16、`_kvf16` f16 KV、`_ub<N>` 預填批次、`_rp1` repeat 1.0、`_t0` 溫度 0、`_share<N>` `--moe-cache-cpu-share`、`_think` 開思考、`_long` 1.5 萬 token 長文生成 32 token、`_longgen` 同長文生成 400 token、`_longctx` 同一對話逐輪加長文。`runs` 是同一個 server 連跑兩次（第 1 次未暖機），`vram_ded`／`vram_shared` 是專用／共用顯存 MiB。第 5、6 點的「長文後新對話」與 n-gram 對照是另外的診斷腳本，數字直接寫在本文。
